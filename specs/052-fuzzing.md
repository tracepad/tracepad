# Spec 052 — Fuzzing the ingest decoders: what strangers' bytes may do to the server

**Status:** ✅ SHIPPED
**Sprint:** October 2026

> The server takes bytes from the network and decodes them: OTLP in two
> encodings, a handful of JSON bodies, cursors and filters out of a URL, the
> text of a search box, a token on a presigned upload. Each decoder has tests
> for the inputs its author thought of, and a decoder is exactly where the
> inputs nobody thought of arrive. Until now the repository held no fuzz test
> at all. This spec adds them — Go's native fuzzing, beside the code, seeded
> from the synthetic corpus — and a way to run them that is not the gate. It
> asserts what every client can see of a bad body: a refusal that says why or
> an acceptance, never a panic, a hang or a 5xx.

---

## Overview

One PR. Deliverables:

- **The targets** (Decisions 1–3): seventeen `func FuzzXxx` in
  `internal/mapping`, `internal/rawid`, `internal/store` and `internal/server`, each next to
  the code it fuzzes.
- **The way to run them** (Decision 4): `make fuzz`, `scripts/fuzz.sh`, and a
  `fuzz` workflow that is started by hand.
- **What the first runs found** (Decision 5): five defects, each fixed with a
  test that fails without the fix.

Not here (*Out of scope*): fuzzing in the gate, a nightly run, a persistent
corpus, the SDKs, and the interface.

Builds on spec 002 (the decoders and the rule that one bad part must not
destroy the rest), spec 019 (the second encoding), spec 041 (the media walk
and the presigned upload), spec 043 (the bounds a body is read under), and
spec 011 (the search parser, whose "FTS5 cannot fail to parse" is a claim
about SQLite).

The two whole-body targets are the ones that pay: everything ingest does with a body runs inside them, so a decoder, the media walk, the mapper or an encoder that panics on a shape the corpus lacks is found by the next mutation of a fixture. |
| 2 | **2026-10-02** — **The invariants are the promises the code already makes.** A body is refused with `ErrMalformedBody` and a message, or it decodes into a tree that can be counted, mapped, walked for media, re-encoded and cut without a panic; the mapping accounts for every span (`observations + skipped = spans`); every trace and observation it makes is one `json.Marshal` can write (a value that cannot be is a lost batch, spec 002 #11); a figure the mapper claims for `usage` or `cost` is a finite number (spec 030 #6); the encoder's output decodes to a tree that maps to the same rows (a round trip); what the media walk extracts is at least `MediaMinSize` and no longer inline in the body it re-encodes; what erasure leaves of a body decodes and holds none of the erased traces. For the handlers: no 5xx, and an answer that says it is JSON is. For the parsers: what is accepted survives being written out and read back (a time through `formatTime`, a cursor through `encodeCursor`), and what is refused is refused with a message. For search: the expression FTS5 is handed is one it accepts, and a snippet is one line of at most `SearchSnippetLength` characters. **A 5xx is the invariant for every handler because the handlers reserve it for a database that failed** (spec 043 #1, #2): a body that reaches one is a bug whichever bytes it was | None of these is a new rule; each is one the code or a spec states and a test checks for the inputs its author had in mind. A fuzz target is the same assertion over inputs nobody chose, so it can only be as good as the assertion: "does not panic" finds the crash, and the rest — the account of every span, the round trip, the finite figure — find the quiet wrong answer, which is what the defects of #5 were. The size of an input is capped at 64 KiB, far under the 20 MiB the server accepts: the body cap is spec 043's and has tests of its own, the mutations are small, and a large seed makes each execution cost half a second and the run a few dozen of them. The large-payload fixtures are therefore not seeds. |
| 3 | **2026-10-02** — **Seeds are synthetic, and the server is built once.** The seeds of the whole-body targets are the bodies of `testdata/otlp/*.pb` that are under 16 KiB, as they are and in the OTLP/JSON encoding, plus the shapes one byte from valid; the seeds of a parser are the cases its unit test names. Nothing under `internal/fixtures-raw` is read (REPOS.md §6). The handler targets that **write** (`FuzzIngest`, `FuzzWrite`, `FuzzMediaUpload`) build a **fresh server on a store of its own for every input**, seven milliseconds each (`freshHarness`), because what a write does depends on what an earlier one left — a dataset's version, a trace's merge — and a crasher that needs the inputs before it cannot be replayed by `go test` from the one file the engine writes; the harness replays the server's log if the input fails. The ones that only read (`FuzzRead`, `FuzzClientAddress`) share **one** server for the process, seeded with the corpus (`newHarness` and `captureLogs` take a `testing.TB` for it, so a `*testing.F` can open one), and discard the log, since the harness's capture of it is a buffer that grows with every request. `FuzzRead` skips a query string over 8 KiB, and `TestReadsWithALongQueryAreAnsweredNotFailed` is what a megabyte of one does on every listing: an answer under two seconds, never a 5xx. A crash is written by the engine to `testdata/fuzz/<Target>/` beside the package, and `go test` replays it ever after as a test: it is committed with the fix | The seeds are the one place a fuzz target can carry something that must not be public, and the rule is the same as for every other fixture. A found input is the regression test; it needs no one to write it, which is the reason to commit it rather than describe it. |
| 4 | **2026-10-02** — **`make fuzz` is a smoke test and is not in the gate; CI runs it by hand.** `scripts/fuzz.sh` finds every `func Fuzz` under `internal/` and runs each for `FUZZTIME` (ten seconds), on `FUZZ_PARALLEL` workers (two), minimizing a new input for at most `FUZZ_MINIMIZE` (five seconds); a failing target does not stop the rest, and the exit status is 1 if any failed. One target: `scripts/fuzz.sh FuzzSearch`. The workflow `.github/workflows/fuzz.yml` is `workflow_dispatch` only, with the time per target and a name filter as inputs; its limit is 350 minutes, and a first step refuses a time that does not fit it with the targets that match (`seconds + 30` each, 340 minutes in all; an iteration count has no length and is refused), so a run is not cut off by the runner with nothing to show. It uploads `testdata/fuzz/` if anything failed or the run was cancelled, so a crasher found before a timeout is not lost. **No schedule yet**: seventeen targets for three minutes each is most of an hour, a night's worth of minutes spent on an answer that changes only when a decoder does. When the repository is public and the nights are wanted, a `schedule:` trigger is the one line it takes | The engine's default minimization is a minute for every input that reaches new code, during which its workers report nothing: a three-minute run of the whole-body target, measured on a loaded machine on 2026-10-02, spent most of its time there and executed a few dozen inputs a minute, against a hundred thousand a second for the response decoder. Only a crashing input is worth minimizing, and five seconds shrinks it. Ten seconds is what a pull request can afford to be told, and finds the shallow ones; the finding worth having took minutes (#5), which is what the workflow is for. Pressing a button is a decision someone makes; a cron is a cost nobody remembers choosing. A local run of minutes is not under the heavy-job lock: it blocks nothing that pushes, and it runs under `nice` (the workers' rules, `AGENTS.md`). |
| 5 | **2026-10-02** — **What the first runs found, and what was done.** (a) **The media walk read `{…}]` as a JSON document.** `decodeDocument` asked `json.Decoder.More()` whether anything followed the value, which is a question about the array or object being read and answers false at a `]` or `}` nobody opened — the trap `decodeStrict` documents in its own comment. A string attribute that held a document and a stray closing bracket was therefore walked, and the media inside it was extracted and the string rewritten, though it is not one JSON value and the rule of spec 041 #1 is that only a string that *is* one is looked into. It asks the decoder for the next token and takes anything but the end of the input as more than one value. (b) **A forged cursor of `NaN` or `Inf` was accepted under `sort=cost`.** `ParseUserCursorKey` takes the key with `strconv.ParseFloat`, which reads both; SQLite binds a NaN as NULL, so the keyset comparison became "no cost" and the answer was a plausible page that was not the page after any row — a wrong answer rather than a refusal. No cursor the server issues holds one (a recorded cost is finite, #2), so it is refused as `invalid cursor` like any other malformed key. (c) **A raw archive cursor had many spellings.** `rawid.ParseCursor` (spec 019 #17) promises that one position has one spelling and refuses anything else, and checked it for the numbers; the base64 around them it read with a lenient decoder, which lets the last character of an unpadded string carry any bits no byte uses (`bjoxOjE`, `bjoxOjF`, `bjoxOjG` and `bjoxOjH` were one cursor) and skips a carriage return or a line feed wherever it finds one (`bjo\r0OjY` was another way to write `bjo0OjY`). It writes back what it decoded and refuses a cursor that is not exactly that. `FuzzRawIDs` found the first from its own seeds in the first second, on the code #189 had just merged, and the second in ten seconds of `make fuzz`; the input is committed under `testdata/fuzz/FuzzRawIDs/` and the three spellings are rows of `TestCursors`. The other cursors (`decodeCursor`) make no claim of one spelling and are as they were. (d) **A body of OTLP/JSON could carry a stray closing bracket after the export.** `decodeJSONNumbers` had the same `More()` in it, so `{"resourceSpans":[]}]` and `…}}` were exports, where the API's strict decoders refuse the shape. `FuzzDecodeExportRequestJSON` now asserts that what it accepts is one JSON value or nothing at all, which is how the first one was found in review and not by a run: the target had no assertion that could. (e) **A data directory whose name is URI syntax opened another file.** `store.Open` put the path into a `file:` URI as it stood, and a `#` ends a URI's path, a `?` begins its query and a `%` an escape, so a directory called `notes#1` was opened as `notes`, and `100%25` and `a#b?c%d` did not open at all or opened what they named by chance. The three characters are escaped (`fileURI`), nothing else is. Found by making a store per fuzz input, whose test names carry a `#`; it is the one defect here that is not about a decoder. Each has a test that fails without the fix: `TestExtractMediaDocumentWithTrailingBracketStaysText` in the mapping package, the two paths added to `TestUserListingRefusesWhatItDoesNotKnow`, the spellings added to `TestCursors` in `rawid`, `TestJSONRefusesMoreThanOneValue` and `TestOpenInADirectoryWhoseNameIsURISyntax`. **Nothing else was found in three minutes on each of the seventeen targets** (fifteen of them ran the three minutes on the tree before #189 and #193 landed and ten seconds on the one after; `FuzzRawIDs` and `FuzzClientAddress` are the two written for what those brought), run one after another under `nice` on a machine with a load average of thirty to seventy: from 28,000 executions (`FuzzIngest`, which committed to one shared database; with a store per input it runs tens a second on that machine) through 198,000 (the JSON export), 667,000 (the protobuf export) and 1.7 million (the scalar readers) to 1.9 million (`FuzzMapAttribute`), with no panic, no hang and no 5xx. That is a statement about those runs and not about the code | None is a crash, and all are what a fuzz target with an assertion beyond "does not panic" is for. All five are small changes, which is the size a defect found by a decoder fuzzer should be if the decoders were written as carefully as their comments say. |

## Testing

- **The targets are tests.** `go test` runs every one over its seeds and over
  every input committed under `testdata/fuzz/`, so the gate replays them all
  in a few seconds and a crash that was fixed stays fixed. Under `-fuzz` they
  are the fuzzers of #1.
- **Mutation** for the five fixes: each of #5's tests fails on the code
  without the change (shown in the PR).
- **The script**: `make fuzz FUZZTIME=2s` runs all seventeen; `scripts/fuzz.sh`
  with a name that matches nothing exits 1; a target that fails is named in the
  summary and the others still run.

## Out of scope

- **Fuzzing in the gate.** Replaying the seeds is in it, by being tests; the
  mutation is not (#4).
- **A nightly run and a shared corpus.** The corpus the engine builds lives in
  the Go build cache of whoever runs it. A corpus checked in or kept as an
  artifact is a thing to maintain for a surface whose invariants are cheap to
  hold, and is the first thing to add if a night finds something a button did
  not.
- **The SDKs and the interface.** Their inputs are their own applications'.
- **Fuzzing the store's SQL, the config, the CLI's flags.** The first takes no
  outside text that is not one of the parsers above; the second and third are
  read from a person's environment and arguments, not the network.
- **A decoder of our own for protobuf.** The envelope is hand-written
  (spec 002 #18) and fuzzed; the generated message types are the library's
  and are not.
