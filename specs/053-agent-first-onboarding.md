# Spec 053 — Agent-first onboarding: one line for the terminal, one line for the agent

**Status:** ✅ SHIPPED
**Sprint:** October 2026

> The quickstart starts with steps a person does by hand: download an archive,
> check it, put it on the path, start the server, copy a key out of a log,
> configure an application, open a browser. A person who already works with a
> coding agent will paste the page into the agent and ask it to do the steps,
> and the agent will then improvise around each one. This spec turns
> onboarding into **two lines**. The first goes into a terminal: it installs
> the binary and the agent skill, verified, with no sudo. The second goes into
> the agent: it points at one page written *for the agent*, which takes the
> project from nothing to a trace the agent has read back itself. The agent
> then tells the person what it did, where the key is, and what is left that
> only a person can do. The documentation is published for agents as well as
> for people: `llms.txt`, and the raw Markdown of every page at a stable
> address.

---

## Overview

Deliverables, one PR (the spec is its first commit; the last commit flips the
status):

- **The install script** (Decisions 2–10): `scripts/install.sh` (POSIX `sh`),
  its offline test `scripts/install-test.sh` against a release built in a
  temporary directory, and `make install-script-test` in the gate, with
  `shellcheck` over both scripts.
- **Where it is served** (Decisions 3, 14): the docs build copies the script,
  `llms.txt`, `llms-full.txt` and every page's Markdown into each version of
  the site. `deploy.sh` mirrors them at the site's root from the version the
  root redirects to.
- **The agent's page** (Decisions 11, 12): `docs/agent-setup.md`, an
  instruction to a coding agent, in the navigation under *Get started*.
- **The skill** (Decision 13): `references/setup.md`, a routing line in
  `SKILL.md` and a setup trigger in its description.
- **The front door** (Decision 15): "With your coding agent" is the first
  block of `docs/quickstart.md` and of the README's *Getting it*, and the
  install script is a section of `docs/install.md`. The manual path stays as
  it is.
- **The audit** (Decision 16): every page of `docs/` read against the
  checklist for agents. Small fixes are made here, and larger findings are
  listed in the PR.

Builds on spec 037 (the skill, `tracepad skills install`), spec 050 (the docs
site, `deploy.sh`, the hook), spec 045 #28 (the first-start key is
`ingest`-only, and declared keys keep all three scopes) and spec 001 #24 (every
`TRACEPAD_*` variable is in `config.Env`).

(d) **The target**: "the latest release" is GitHub's `releases/latest`; no stable release yet is said, with the newest candidate named and asked about. A named version is taken as said. **An older version is refused**, with the reason: migrations run forward only, and the way back from an upgrade is the backup taken before it. (e) **The backup comes first**, in `~/tracepad-backups/<time>-<from>/`, outside the data directory, `umask 077`. It holds the trace count (`tracepad system`, the project view's `rows.traces`; empty when the key cannot read), the old binary when it is still the installed one, and a `state` file that the check and the way back read, because an agent's shells do not keep variables (#18). The command stops before changing anything when `df` shows less room than `du` says the data directory takes. For the binary the data directory is archived with the server stopped (a tar of a live database is a copy mid-write, `docker.md`); for a container, the volume is archived from the stopped container with `busybox`, as `docker.md` does. (f) **The restart.** The binary: the install script with `TRACEPAD_VERSION` and `TRACEPAD_NO_SKILL=1`, the server stopped by its PID (fifteen seconds, never `kill -9`), the archive, the new binary started with the same `--listen` and `--data-dir` and `TRACEPAD_URL` from the listen address. `TRACEPAD_PROJECTS` is not needed again: declared projects are created at the first start and never rotated by the variable (`docker.md`). The container: the exact tag pulled, the old container stopped and kept, renamed `<name>-<from>`, and a new one run with its volumes, ports, restart policy and `TRACEPAD_*` variables (through an env file in the backup directory, so the secrets are never on a command line). (g) **The check**: the log's first line names the new version and its commit (spec 001's start label, #216), `health` says the new version, the trace count is at least what it was, and `setup.md`'s test span answers `200` and reads back. A migration in progress is waited for, not rolled back. (h) **The way back** runs at once when the new server does not start or `health` fails; when it runs but a check looks wrong, the person is asked first, because going back drops what arrived since. It restores the database's files only (not the log, the lock or the server's own `pre-<NNNN>` backups), puts back the old binary (the copy, or the install script pinned to `from` when the script had already replaced it), and starts it the same way; for a container, the volume is restored and the old container renamed back and started. (i) **The skill and the package**: the skill is installed again wherever a `tracepad/.version` marks a copy, the way it went in (`--dir`, `--project`, or the image with `-v` when the host has no binary). A pinned `tracepad` package moves to the same version in the project's own tool: PyPI's `0.1.0rc2`, npm's exact `0.1.0-rc.2` (`next` is the newest candidate, which may be another), Go's `sdk/go@v0.1.0-rc.2`. The project's tests run. A version not published leaves the pin, and the report says so. (j) **The install script names the servers it left behind** (amends #9). After it replaces a binary, it lists every `tracepad serve` whose executable is that binary — the path from `/proc/<pid>/exe` on Linux, from `lsof` on macOS (both still name it after the rename), the command's first word when neither can say — with its PID and command line, and how to restart it. A server started as a bare `tracepad` on the `PATH`, as `setup.md` starts one, is found too, and so is one on any port. The probe of `localhost:4318` remains for when none is found: a container, or a server from another binary. After an update, the last line is the upgrade line with the new version, `Update Tracepad to X: follow …/agent-upgrade.md`, since the setup line is for a project that has nothing yet (amends #1 and #4 (7)). The offline test gains stand-ins for `ps` and `lsof`. (k) **Docs**: `docs/agent-upgrade.md` in the navigation after *Agent setup*, the agent line at the top of `install.md#upgrading` and `docker.md`'s upgrade section, a sentence in the quickstart and the README; `llms.txt` picks the page up from the navigation (#14). (l) **Budgets**: `upgrade.md` is 180 lines. `SKILL.md` stays at 200; the whole skill is 1090 lines, the budget spec 037 #19 sets. (m) **The live run**, in a clean `HOME` on a spare port, each block run as the file has it, with only the install script's address pointed at a temporary mirror: the real `0.1.0-rc.1` installed by the script and started as `setup.md` starts it, two test spans; then `upgrade.md` to a `0.1.0-rc.2` built from this branch and published in the mirror with its checksum. Step 1 marked the agent's server `MINE` and another server on the machine `OTHER`. The script, in step 3, named the running server by `lsof` (started as a bare `tracepad`) and ended with the upgrade line. The check read the log's `tracepad 0.1.0-rc.2 (<commit>)`, `health` at the new version, 2 traces before and 3 after a new span read back. The way back restored `0.1.0-rc.1` and its 2 traces. A second upgrade, then a release whose binary will not serve: the check said *NOT HEALTHY*, and the way back put `0.1.0-rc.2` back with its data. The skill went from `0.1.0-rc.1` to `0.1.0-rc.2`, with `setup.md` and `upgrade.md`. The Docker blocks ran against a stand-in `docker` that logs its calls: the new container got the volume, the loopback port, the restart policy and the `TRACEPAD_*` variables through the env file, and the way back stops before touching the volume when there is no archive. **Fixed from it**: the container block had no `PATH` for the CLI, and its Compose check passed when `docker inspect` failed; a block that stopped early left an empty backup directory that the check then took for the newest (the check and the way back now take the newest with a `state` file, and the container block makes its directory only after its checks); the way back reset no log offset; the check printed values but no verdict, so it now ends *NOT HEALTHY* with exit `1`, and the way back makes it expect `from`; the skill step exited `1` when the last copy was absent. | An update is where a person has the most to lose: the data the server holds. Before this, the agent knew only setup, and an install script that replaced the binary left the running server on the old version with nothing but a hint about `localhost:4318`. The procedure is one an agent runs as written, so it lives where the drift test reads it and the version matches the binary. Each rule closes one way the agent could leave a person worse off: no backup, a downgrade onto a migrated database, a restarted server that is someone else's, a container recreated without its volume or its keys, a way back that deletes the evidence. |

## Application contract

- `scripts/install.sh`: POSIX `sh`. Reads `TRACEPAD_VERSION`, `TRACEPAD_INSTALL_DIR`,
  `TRACEPAD_NO_SKILL` and `TRACEPAD_DOWNLOAD_URL`, and nothing else from the
  `TRACEPAD_*` space. It needs `curl`, `tar`, `uname`, `mktemp` and `sha256sum`
  or `shasum`; `gh` is optional. Exit `0` on success, `1` on any failure, with
  the reason on stderr. The summary goes to stdout, and its last line is the
  agent line.
- `internal/config/env.go`: the `EnvInstaller` kind and its four variables.
  `cmd/tracepad/env_test.go`: the script reads exactly those.
- `scripts/docs-site/hooks.py`: the per-page Markdown, `llms.txt`,
  `llms-full.txt`, and the copy of `install.sh` into the build, with tests in
  `hooks_test.py`.
- `scripts/docs-site/deploy.sh`: after `set-default`, a commit that copies
  `install.sh`, `llms.txt`, `llms-full.txt` and `*.md` from the default
  version's directory to the branch's root, and deletes root files of those
  kinds that the version no longer has.
- `docs/agent-setup.md` (new), in `mkdocs.yml` and `docs/index.md`.
- `agent/skills/tracepad/references/setup.md` (new); `SKILL.md`.
- `agent/skills/tracepad/references/upgrade.md` (#21, new), its routing line
  and trigger in `SKILL.md`, and `docs/agent-upgrade.md` (new), in
  `mkdocs.yml` after *Agent setup*. `scripts/install.sh` names the servers
  still running a binary it replaced, and ends with the upgrade line after an
  update.
- `Makefile`: `install-script-test`, in the gate.
- `.github/workflows/site.yml`: `scripts/install.sh` in the paths of a `dev`
  deploy.

## Edge cases

- **No stable release yet** (true until 0.1.0): exit `1`, with the pinned line
  (#5).
- **A pinned version that does not exist**: the download of its
  `checksums.txt` fails. The message names the version and the releases page.
- **A server already at `localhost:4318`, not started by the agent**: the
  agent asks for a key (#12) and does not start a second server.
- **No server running, but the default data directory already holds a
  `tracepad.db`** (an earlier install): the directory is not fresh, so the
  agent does not declare a key. It asks the person whether to start that
  server, which falls under the fallback of #12, or to use a new data
  directory for this project.
- **The port is taken by something that is not Tracepad**: `tracepad health`
  fails while the port is open. The agent picks another port with
  `--listen`, and every address it writes uses that port.
- **`.env` is not ignored by git**: the agent adds it to `.gitignore` before
  writing the key, and says so in the report (#12). If `.env` is already
  tracked, ignoring it does not untrack it, so the agent writes no key there
  and asks the person where the key should go.
- **macOS quarantine**: `curl` sets no quarantine mark, so Gatekeeper does not
  apply (`install.md`).
- **An install directory that holds a `tracepad` the script did not put
  there** (from Homebrew, say): `~/.local/bin` is not Homebrew's directory, so
  nothing is overwritten. The summary says which `tracepad` comes first on
  `PATH` when that is not the one just installed.

## Out of scope

- A Windows installer (PowerShell). The Windows archives are in
  `install.md`.
- Installing a service (systemd, launchd) from the script: that outlives the
  session and is the person's decision (`install.md` has both).
- Editing shell profiles or agent configuration files (MCP blocks) for the
  person.
- A custom domain for the site, which would change both lines' addresses.
- Listing the script on third-party skill or installer registries.
