# Spec 001 — Server Skeleton

**Status:** ✅ SHIPPED
**Sprint:** August 2026

> The minimal runnable Tracepad: a single binary that starts an HTTP server,
> owns a self-migrating SQLite store, bootstraps projects with API keys, and
> answers `/health`. Everything later (ingest, read API, UI) builds on this
> foundation, so this spec fixes the binary layout, configuration surface,
> storage bootstrap, and release plumbing.

---

## Overview

Deliverables:

- `tracepad` binary: `tracepad` / `tracepad serve` runs the server,
  `tracepad version` prints the version.
- Configuration via `TRACEPAD_*` environment variables with flag mirrors.
- SQLite store (pure-Go driver) with embedded forward-only migrations that
  apply automatically on start, taking a file backup first.
- Project + API key model with first-run bootstrap and declarative
  `TRACEPAD_PROJECTS` provisioning.
- `GET /health` returning `{"status":"ok","version":...}`.
- Make targets (`build`, `test`, `precommit`, …), GitHub Actions CI,
  GoReleaser config for the six-platform release matrix.

## Decisions log

| # | Decision | Why |
|---|---|---|
| 1 | Bare `tracepad` (no args) runs the server | The target experience is "download, run, works". Requiring `serve` is a paper cut for the primary flow; subcommands still exist for everything else. |
| 2 | Default listen address is `:4318` | 4318 is the OTLP/HTTP convention port, and OTel SDK exporters default to `http://localhost:4318`. A locally running Tracepad therefore receives traces from an unconfigured OTel app with zero endpoint setup. UI and API share the same port (single-binary, single-port). |
| 3 | CLI is stdlib `flag` + manual subcommand dispatch, no framework | Stage 0 has two subcommands; a CLI framework is not paying for itself yet. Revisit in the stage-2 spec (read-side CLI with many subcommands and global `--json`) — this decision is expected to be renegotiated there, and the dispatch code is small enough to throw away. |
| 4 | API secrets are hashed with SHA-256, not bcrypt | Keys are generated 256-bit random strings, so offline brute force is infeasible and slow hashing adds nothing. bcrypt would cost ~100ms *per request* on the hot auth path and pull in `x/crypto`. bcrypt/argon2 are for low-entropy human passwords, which we do not have (no user accounts by design). |
| 5 | SQLite driver is `modernc.org/sqlite` (pure Go) | CGO-free static cross-compilation for the whole release matrix without C toolchains. ~2× slower writes than the CGO driver is irrelevant at our load profile (design gives ~100× headroom). The store interface stays narrow so the driver can be swapped locally if the CI benchmark gate (later stage) ever trips. |
| 6 | Migrations: embedded files `NNNN_name.sql`, forward-only, tracked by filename in `schema_migrations`, lexicographic order, file backup before applying | Zero-devops constraint: the binary must self-heal its schema on start with no operator action. Forward-only avoids down-migration testing surface. A copy of the DB file (`<db>.pre-<first-pending>.bak`) before applying pending migrations makes every upgrade trivially reversible by file swap — appropriate for an embedded single-file DB. |
| 7 | All tables are SQLite `STRICT` | Catches type mistakes at insert time instead of storing garbage; costs nothing. New tables must follow suit. |
| 8 | One key pair (`tp-pk-…`, `tp-sk-…`) per project serves both native and compat auth | Native auth is `Bearer <tp-sk>`; the future Langfuse-SDK path uses `Basic base64(pk:sk)` with the same pair. Langfuse SDKs do not validate key prefixes, so one pair covers both wire formats. Secret lookup is by `sha256(secret)` (unique index) so Bearer auth needs no key id in the token. |
| 9 | `TRACEPAD_PROJECTS="name:pk:sk,…"` declarative bootstrap, idempotent | docker-compose reproducibility: a restarted container must not mint new keys. Existing project names are left untouched (keys are not rotated by env), missing ones are created with the given pair. First run without the variable creates project `default` with generated keys and prints ready-to-paste OTel and Langfuse env lines. |
| 10 | Logging is `log/slog`, text handler to stderr | stdlib, structured, zero deps. File logging with rotation is a later concern (self-diagnosis stage); stderr is correct for both `docker logs` and dev. |
| 11 | (2026-08-26, from PR #1 review) Pre-migration backups use `VACUUM INTO`, not a file copy | A plain copy of the main DB file silently loses committed rows still sitting in the WAL (reproduced: after an unclean shutdown the copied file restored an empty database), betraying exactly the scenario backups exist for. `VACUUM INTO` produces a complete checkpointed snapshot and streams it without loading the DB into memory. The snapshot is defragmented, not byte-identical — irrelevant for restore-by-file-swap. |

| 14 | **2026-09-26** — **Every response carries four headers**: `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: same-origin`, set by one middleware before any handler runs. A `script-src` policy has to be written against what the interface's bundle actually loads (the editor, the charts, inline styles) and tested screen by screen; it is a spec of its own, not a header added in passing. |
| 15 | **2026-09-26** — **The transport bounds how long a response may take to write, and does not cap connections.** `WriteTimeout` is **5 minutes** for every response. The one exception is MCP (`/mcp`), a stream whose length is the tool's: it lifts its own deadline through `http.ResponseController`, and only **after** the request's `Authorization` has resolved to a live project's key, read by the one function the guard reads it with; anything else — a soft-deleted project's key, a key without the `read` scope (spec 045 #1) and the admin token included, since every MCP tool is a read and the admin token reaches no data-plane route (spec 028 #3) — is answered `401` with `WWW-Authenticate: Bearer` under the ordinary deadline, and a store that cannot answer is `503` with `Retry-After` and without the challenge, as the guard answers it (spec 043 #1), and `/.well-known/*` is the API's JSON 404 rather than the interface's page. The read deadline is not lifted: net/http clears it once the body has been read, so a tool call outlasting `ReadTimeout` is not cancelled, and clearing it earlier would drop the bound on a slow body. The five minutes count from the end of the request headers, so they bound a handler's work too; that is documented rather than lifted, since no route but MCP's is meant to run that long and bulk deletion already works in bounded rounds per request. There is no server-wide limit on connections. Request-reading deadlines per handler are not this decision: they belong with the ingest bounds of a later spec | Without a write deadline a client that reads one byte a second held a connection for as long as it liked. Five minutes is what the largest ordinary response — one 20 MiB body, a media file or a raw batch — needs over a link of about half a megabit, and it bounds a slow reader to that. The stream is lifted for a credential only, because a deadline that anybody can switch off is not a bound; the `WWW-Authenticate` and the JSON `/.well-known` are for the MCP client that meets that 401 and goes looking for OAuth metadata, which found the interface's HTML and failed on parsing it rather than saying a key was missing. A connection cap was tried and removed in review: a cap that counts every connection alike, with no notion of who holds them, is itself the outage — five hundred silent connections from one anonymous client, each holding its slot for the header timeout, keep every browser and exporter waiting — where without it the same client needs thousands of descriptors. Limits per client belong with the rate limiting of a later spec. |
| 16 | **2026-09-26** — **A stop waits for the handlers it interrupts, and says when it could not.** SIGINT/SIGTERM drains for **5 seconds**; whatever connection is still open then is closed with a `WARN`. Closing a connection does not stop its handler, so the server then waits up to **3 seconds** for every handler to return — counted by a middleware — on every path out of Shutdown, whatever else failed, then writes the key uses those handlers made (spec 045 #9, a single small job) in at most a second, within what is left of those three and never under a quarter of one, and only then does its owner close the writer, the sweeper and the aggregator. Once that wait has begun no handler starts: a connection goroutine that had already read a request when its connection was closed is answered `503` rather than let in behind the wait's back. MCP streams end when the stop begins — their context is tied to it — so a connected client does not hold the drain for its whole window; nothing else is, so an ingest waiting on its commit is left to finish. A second SIGINT/SIGTERM during the stop kills the process, as it would without a handler. A `Serve` that fails on its own takes the same stop before the process closes anything, since the connections it accepted may still be running handlers. Every handler returned: exit 0. One still running after the three seconds: a `WARN`, and exit 1 | Shutdown returned the drain window's deadline as an error, so a stop asked for and carried out exited 1, and a supervisor read an ordinary `docker stop` as a crash; but closing the connections and returning at once would have closed the writer under an ingest handler still waiting on its commit, and the exporter would retry a batch that may have landed. Waiting for the handlers keeps the order the writer relies on — every submitter done before it closes — and exit 1 is kept for the case that really is unclean. Five and three — the key-use write inside the three — because together they leave two of the ten seconds `docker stop` and Compose allow before they kill for what closes after them — the aggregator, the sweeper, the writer and the store, each of which may be finishing a commit or a checkpoint: a stop that overran would lose the ordered close entirely and exit 137. The windows are fixed, not configured, so a longer `--stop-timeout` gives nothing more; a setting for them is a later change's, if anyone needs one. |

| 20 | **2026-09-29** — **One server per database.** `tracepad serve` takes an exclusive, non-blocking lock on `<database>.lock` (`tracepad.db.lock`, beside the database it protects) before it opens the database and holds it until it exits; a second `serve` on it exits at once with `another tracepad is already running on the database <path> (the process that last recorded itself there had pid <N>, which may be stale or another container's): stop it, or give this one a directory of its own with --data-dir`. The lock is `flock` on Linux, macOS and the BSDs and `LockFileEx` on Windows, taken on the open file, so it goes when the process does — a killed server leaves nothing to clean up. The holder writes its pid into the file, only so that the refusal can offer it as a hint, and a failure to write it is a `WARN`; the lock, not the number, is the truth. On Windows, where locks are mandatory, the locked byte is far past the pid (offset `0x7fffffff`), so a refused server can still read it. A file system that cannot lock (`ENOLCK`, `ENOTSUP`, `ENOSYS`, `EOPNOTSUPP`; `ERROR_NOT_SUPPORTED`) is a `WARN` that the directory is unguarded, and the server starts: a deployment that ran on it yesterday runs on it today, as `files.go` treats a file system without modes (spec 044 #12). The file is `0600`, created by the lock and tightened at every start with the database's own files, and it is one of them — for `tightenDir` and spec 044 #18 — only as `<database>.lock`, so a directory that holds another database's lock file is not thereby the server's. It is easy to do: a Docker restart that overlaps its predecessor, `make dev` beside a server nobody stopped. A pid file would need a stale-file rule for a server that was killed; `flock` needs none. ## Configuration

| Env | Flag | Default | Meaning |
|---|---|---|---|
| `TRACEPAD_LISTEN` | `--listen` | `localhost:4318` | HTTP listen address; `localhost` is both loopback addresses (Decisions 22, 23; the image sets `:4318`) |
| `TRACEPAD_DATA_DIR` | `--data-dir` | `$XDG_DATA_HOME/tracepad` or `~/.local/share/tracepad` | DB + future payload storage |
| `TRACEPAD_PROJECTS` | — | empty | Declarative project bootstrap (Decision 9) |
| `TRACEPAD_ADMIN_TOKEN` | — | empty | Cross-project admin token (spec 005); at least 32 characters (Decision 18) |
| `TRACEPAD_ADMIN_TOKEN_FILE` | — | empty | A file to read the admin token from instead; not with `TRACEPAD_ADMIN_TOKEN` (Decision 18) |

Flags override env. Unknown `TRACEPAD_*` variables are a startup warning (typo
detector), not an error.

## Data contract (schema 0001)

```sql
projects(id TEXT PK, name TEXT UNIQUE, retention_days INT DEFAULT 30, created_at)
api_keys(public_key TEXT PK, secret_hash BLOB UNIQUE, project_id → projects, created_at)
```

`schema_migrations(filename TEXT PK, applied_at)` is created by the migration
runner itself, outside numbered migrations.

## Edge cases

- Data dir missing → created with 0700; an existing one, and the database files, are tightened to 0700 and 0600 at every start (#13, spec 044 #13).
- DB from a newer binary (unknown migration recorded) → refuse to start with a
  clear error naming both versions; never run "unknown future" schemas.
- Corrupt WAL → SQLite recovers on open; if open fails, the error names the DB
  path and the latest `.bak` file.
- Duplicate names in `TRACEPAD_PROJECTS` → startup error (ambiguous intent).
- Backup file already exists (re-run after crashed migration) → overwrite; the
  pre-migration state of *this* run is what matters.
